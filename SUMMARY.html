The Flaky Network

Architecture and design summary — real-time frame delivery over a lossy, jittering, reordering, duplicating relay.

STREAM 160 B / frame @ 20 ms  ·  TRANSPORT UDP, 127.0.0.1  ·  LANGUAGE C++17
MECHANISM rate-½ XOR convolutional erasure code, stride 1  ·  FEEDBACK none
RESULT profile B, 30 s, 100 ms playout → 0.13 % miss, 1.95× overhead, VALID

1. What the problem actually is

A source hands the sender frame i at exactly t0 + i·20 ms. The player judges frame i at t0 + DELAY_MS + i·20 ms: the payload must have arrived on port 47020, byte-correct, before that instant. Between the two sits a relay that drops packets, delays each one by an independent random amount, duplicates some, and thereby reorders them.

The naive forward gives 3.8 % misses on profile A and 40 % on profile B. Decomposing that number is the whole design:

miss(frame i)  ≈  P(packet lost)  +  P(network delay > DELAY_MS)
                  └── drops ──┘      └──── jitter tail ────┘

On profile B, loss is 5 % but the delay is uniform on [20, 80] ms. At a 60 ms deadline the jitter tail alone accounts for roughly a third of all frames. Jitter, not loss, is the dominant failure mode, and the two require different remedies: jitter is bought off with playout delay or with independent delay draws, loss is bought off with redundancy.

2. The constraint that decides everything

score.py defines raw = n × 160 and charges every byte crossing the relay in both directions, including packets the relay subsequently drops. The cap is 2.0×. So the entire budget is:

320 bytes per frame, sender + receiver combined.

Plain duplication is arithmetically impossible. Two copies of a 160-byte payload is 320 bytes before a single header byte. Any scheme that repeats every frame in full is over the cap by construction. The real budget is about 1.95×, i.e. roughly 0.9 redundant packets per frame — slightly less than one.

Two corollaries followed immediately, and both shaped the implementation:

  • Every feedback byte is media budget spent. The receiver therefore sends nothing at all; the whole 2.0× stays on the forward path.
  • Header size is a first-class cost. At 163 B/packet the header is 1.9 % of the budget. A 4-byte sequence number would have cost measurably more redundancy, so the wire sequence is 16-bit.

3. Why FEC, and why this FEC

Retransmission was rejected on arithmetic

A NACK crosses the relay to the sender and the repair crosses back — two independent draws from the same hostile distribution. On profile B that is two samples of [20, 80] ms, so the expected repair lands ~100 ms after the loss is even detected, on top of the detection delay. There is no playout delay worth scoring that absorbs it. ARQ is the correct mechanism when the round trip is small relative to the deadline; here it is larger.

Parity beats repetition at identical cost

One redundant packet per frame can carry either a copy of an old frame or an XOR of two frames. They cost the same bytes. The XOR carries strictly more information:

SchemeCostRecovery paths for frame i
Repeat frame i immediately~2 pkt/frame2, both at lag 0 — dies whole in a burst
Repeat frame i at lag L~2 pkt/frame2, one at lag 0 and one at lag L
XOR parity, stride S~2 pkt/frame3 — see below

With parity[i] = frame[i] XOR frame[i−S] transmitted right behind frame[i], frame i can be reconstructed from any of:

  1. its own data packet — lag 0;
  2. parity[i] XOR frame[i−S] — lag 0, since frame[i−S] is already decoded;
  3. parity[i+S] XOR frame[i+S] — lag S, the burst-survival path.

The same byte buys both a zero-lag repair and a future repair. That is the design's central claim.

Stride was measured, not assumed

Stride 3 was the initial choice on the theory that spreading redundancy decorrelates it from bursts. It measured 1.0 % on B at 90 ms and refused to improve at 110 ms — a plateau, meaning the residual misses were not jitter. Replaying the receiver's actual packet log through an offline decoder with no time limit showed only 2 of 1000 frames were truly unrecoverable while 9 were scored as misses: seven frames were repaired after their deadline.

Stride is a delay tax. Path 3 is not transmitted until t = 20(i+S), so it starts 20S ms behind and then draws its own network delay. At S=3 that repair cannot beat a 100 ms deadline more than about half the time. Sweeping S ∈ {1,2,3} was monotone on every profile tested, including the bursty ones: S = 1 wins. Widening the stride cannot decorrelate the burst anyway, because the data packet and its parity are emitted back-to-back and a burst takes both regardless — stride only relocates the third path, further into the future.

4. System architecture

Wire format (sender → receiver, our design)

byte 0        type   0 = data, 1 = parity
bytes 1–2     seq    uint16 big-endian
bytes 3–162   160 B  payload, or frame[seq] XOR frame[seq−S] for type 1
                                                        total 163 B

A 16-bit sequence covers 65 536 frames ≈ 21 minutes at 20 ms, comfortably beyond any graded run, and the receiver zero-extends it to the 32-bit sequence the player expects. Data and parity share one format, so a duplicate arriving from the relay and a redundant packet sent on purpose are handled by the same code path.

5. Sender

Single-threaded, blocking recvfrom on 47010. There is nothing to schedule: the source's own clock is the pacing, and the sender is physically unable to transmit frame i early because it does not yet have it. Per frame:

  1. Parse the 4-byte big-endian sequence, store the payload in a flat history array indexed by sequence.
  2. Emit the data packet immediately — latency here is pure loss, so nothing is buffered or batched.
  3. If seq ≥ S and the governor permits, XOR against history[seq−S] and emit the parity packet.

The byte governor

allowed = RATIO × 160 × (seq + 1)          // RATIO = 1.95
if (bytes_sent + 163 <= allowed) { emit parity; bytes_sent += 163; }

This is a cumulative check, not a per-frame one, so it self-corrects: transient suppression is repaid as the allowance grows. It costs roughly 8 % of parity packets — the price of header bytes — and in exchange the run is structurally incapable of breaching the cap on any profile, measured or unmeasured. Overhead came out at exactly 1.95× on every run recorded. Making the limit a property of the code rather than of a tuned constant is what makes the result portable to the unseen grading profiles.

6. Receiver

No playout clock — and that is the point

Reading endpoints.py closely: the player records first_arrival[i] and later asserts arrival ≤ deadline. Nothing penalises early arrival. The graded jitter buffer is therefore the DELAY_MS parameter itself, held by the harness. A scheduler on the receiver could only ever delay a frame toward its deadline, never improve it. So the policy is: the instant a payload becomes known, emit it. This removed an entire thread, a timer, and a class of bugs.

Decode cascade

State is four flat arrays indexed by sequence — payload, have, sent, parity + have_parity. A parity at index p spans frames p and p−S and is resolvable exactly when one of the two is known:

on data[s]    : if !have[s] → store, deliver, cascade(s)
on parity[p]  : if !have_par[p] → store, cascade(p)

cascade(x)    : queue ← x
                while queue non-empty:
                    y ← pop
                    try_resolve(par[y])        // spans y and y−S
                    try_resolve(par[y+S])      // spans y+S and y
                    any frame recovered → deliver + push

The cascade matters because repairs chain: a parity held in limbo because both its frames were missing becomes resolvable the moment a neighbour is recovered, which may in turn unlock the next parity along the chain. An explicit work queue is used rather than recursion, since a cascade can run the length of the stream.

Bug found by measurement, not by reading. An early version called try_resolve before cascade on parity arrival, so it pushed onto a queue whose indices were then reset — repairs happened but never propagated. It was invisible in the miss rate and only surfaced when the offline decode of the packet log disagreed with the harness score. Instrument the decoder against ground truth; the score alone will not tell you whether a mechanism is weak or merely mis-wired.

Because the relay redraws impairments per packet, a delay tuned on one seed is fitted to noise. 100 ms was the lowest value that held across every seed and both self-authored burst profiles.

8. Known failure modes

  • Bursts longer than ~2 frames. A rate-½ chain repairs at most one erasure per parity, and the data packet and its parity are emitted back-to-back, so a burst takes both. On a self-authored harsh profile (70 % in-burst loss, mean burst ≈ 4 packets) the miss rate plateaus near 2 % and no amount of playout delay recovers it — the frames are unrecoverable, not late. Fixing this needs a stronger code, which the 2.0× cap forbids, or a wider stride, which the deadline forbids. The constraint pair is the binding one, not the mechanism.
  • Jitter tail beyond ~95 ms. The last repair path is only 20 ms behind the data; past that, misses are deadline-bound rather than mechanism-bound, and the only remedy is a larger delay_ms.
  • Sustained loss above ~15 %. The governor keeps overhead legal by suppressing parity, so under heavy loss the code silently weakens exactly when it is most needed. An adaptive scheme would need feedback, which costs budget on the same meter.
